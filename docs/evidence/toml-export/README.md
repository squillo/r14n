# Acceptance pair — generating a published pack from its typed Snapp source

> **⚠ NOT LEGAL ADVICE.** The packs referenced here are machine-readable templates of
> controls, not statements of any jurisdiction's law. **"aggressive" ≠ "compliant."**
> See [`../../not-legal-advice.md`](../../not-legal-advice.md).

`recording_consent` is the one domain this repository ships in **both** representations: a
typed N Lang Snapp source and a published `.r14n.toml`. That makes it the only domain where
"the published artifact is generated, not hand-maintained" can be *proved* rather than
asserted — so it is the acceptance pair for a TOML export format in the N Lang toolchain.

Today the TOML is hand-maintained and the two are held in agreement by a test
(`resolver/tests/snapp_toml_parity.rs`), which compares **values** and is blind to
serialization. This directory states what the generated bytes would have to be.

## The pair

| Role | Path |
|---|---|
| Source (typed) | `baselines/1.0.0/lib.n.md` — the `policies` keyword form |
| Emitted bundle | `snapp/r14n_baselines@1.0.0.json` — key `policies.RECORDING_CONSENT_AGGRESSIVE` / `…_MINIMAL` |
| Published artifact | `packs/{aggressive,minimal}/recording_consent.r14n.toml` |
| Expected export output | `expected/recording_consent.{aggressive,minimal}.toml` (this directory) |

The expected files are the published packs' **non-comment bodies**, byte-for-byte. They are
not hand-written: `tools/tests/toml_export_acceptance.rs` re-derives them from the published
packs on every run, so a fixture that drifts from its pack fails the build rather than
quietly becoming a second source of truth.

## Acceptance

An exporter passes when, for both profiles, its output **parses to the same TOML value tree**
as the matching `expected/` file.

Value equality, not byte equality, and deliberately: the two published packs do not agree on
table ORDER (`aggressive` puts `[legally_required]` last, `minimal` puts it before the
subjects). A serializer emits in one order. Demanding byte equality would therefore fail one
of the two profiles no matter which order the serializer chose, for a difference no consumer
can observe.

## Three deltas, stated up front

**1. Comments do not survive.** The published packs carry substantial hand-written prose —
the control vocabulary is documented inline, and `[meta.legal_review]` carries the reason the
status is what it is. None of it exists in the source tree, so none of it can be emitted. A
generated pack is a *less documented* pack unless something else carries that prose.

**2. The header preamble has to come from somewhere.** Every published artifact in this
repository opens with an SPDX line and the NOT-LEGAL-ADVICE notice — that is invariant 3, and
it is not decorative: it is the thing that keeps a control template from reading as a legal
claim. A serializer that emits only the value tree produces an artifact that **violates the
invariant on arrival**. Either the exporter accepts an author-written passthrough preamble,
or generated packs cannot be published here at all.

**3. The field names do not match, and this is the one that decides scope.**

| Emitted bundle | Published TOML |
|---|---|
| `subjects` (plural), keyed map | `[subject.<key>]` (singular) |
| `legally_required: [ … ]`, bare list | `[legally_required]` with `controls = [ … ]` |
| `domain: "recording_consent"` | absent — the filename carries it |

A **straight** serialization of the emitted object tree therefore does not produce a valid
pack: it writes `[subjects.local_piggyback]` and a bare `legally_required` array, neither of
which validates against `schema/pack.schema.json`, and it writes a `domain` key the schema
does not allow at top level.

There are two ways to close that, and they land in different places:

- **The exporter projects.** It renames and wraps on the way out. The projection is
  pack-specific knowledge living in a general-purpose tool — the exporter would have to know
  what an RLPS pack is.
- **The type is renamed instead.** `subjects` → `subject`, and `legally_required` gains a
  `controls` field, in `r14n Spec/1.0.0/…/R14N_SPEC_KEYWORD_POLICIES_1_0_0.n.md`. Then a
  straight serialization is already correct and the exporter needs to know nothing about
  packs.

The second is the DRY answer and it is **this repository's** change to make, not the
toolchain's. Its cost is not small: re-emitting both bundles, refreshing the integrity pin in
the same change (invariant 11), and a matching re-emit in the downstream consumer repository,
whose adapter currently absorbs exactly this mismatch in a projection step that would then
become dead code. It is tracked here rather than done silently, because doing it mid-flight
in two repositories is how a pack ships half-migrated.

`tools/tests/toml_export_acceptance.rs` asserts these three deltas **as they are today**. If
the rename above happens, that test goes red on purpose — it is the signal that the exporter
no longer needs a projection, and the signal is worth more than the test passing.
